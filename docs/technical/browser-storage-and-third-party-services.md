# Хранилища браузера и сторонние сервисы YUME

**Основание:** проверка репозитория и публичного Worker 2026-10-27. Это технический реестр наблюдаемого поведения, а не юридическое заключение.

## Browser storage

| Ключ / источник | Назначение | Где хранится | Оговорка |
|---|---|---|---|
| `yume-language` | Язык интерфейса | localStorage | Не облачный профиль |
| `yume-theme` | Тема | localStorage | Не серверный аккаунт |
| `yume-cookie-notice-acknowledged` | Старый флаг закрытия уведомления | localStorage | Сам по себе не подтверждает согласие |
| `yume-favorite-anime-v1` | ID сохранённых тайтлов | localStorage | Нет облачной синхронизации |
| `yume-watchlist-anime-v1` | ID списка просмотра | localStorage | Нет облачной синхронизации |
| `yume-cookie-consent-v1` | Явный выбор necessary/analytics и время выбора | localStorage | Не включает аналитику без `analytics=true` |
| `yume-analytics-consent` | Серверно читаемое значение all/necessary | cookie | В тесте не содержит user ID |
| `yume-analytics-visitor-id`, `yume-analytics-session` | Аналитические идентификаторы | localStorage | Создаются при разрешённой аналитике; удаляются при отказе |

Код содержит заготовки для прогресса просмотра, но это не следует описывать как работающую историю просмотра, пока не подключён реальный плеер и не работает соответствующий пользовательский сценарий.

## Сторонние сервисы

| Сервис | Текущая роль | Следующее требование |

| Cloudflare Workers / Nitro | Выполнение приложения, входящие запросы | Проверить договор, IP/access/security logs, retention, regions и условия обработки |
| Cloudflare D1 (YUME_DB) | Метаданные каталога | Проверить размещение, резервные копии и доступы; не путать с базой профилей |

| VK ID / Яндекс ID | Не подтверждены как production-интеграции | OAuth credentials, redirect URI, поля, сессии, удаление профиля |

## Проверка production: HTTP и HTTPS

Дата: 2026-10-27. URL: https://yume-website.yumesupport833.workers.dev/

- Запрос к `http://yume-website.yumesupport833.workers.dev/` получил **308 Permanent Redirect**, `Location: https://yume-website.yumesupport833.workers.dev/`, без тела страницы. Следовательно, содержание по открытому HTTP не выдаётся.
- HTTPS-страница ответила HTTP 200.
- Реализация `src/lib/https-redirect.ts` сохраняет path/query в редиректе, исключает loopback для local development и удаляет порт 80; unit-тесты проверяют эти случаи.
- Политика доступна по ссылке `https://yume-website.yumesupport833.workers.dev/?section=privacy-policy`, ответ HTTP 200 и HTML содержит текст политики. Не удалось подтвердить её юридическую достаточность в рамках технического скана.

## Shikimori cookies

Прямой HTTP-запрос к `https://shikimori.io/` и к изображению постера возвращал `Server: ddos-guard` и `Set-Cookie` для `__ddg1_`, `__ddg8_`, `__ddg9_`, `__ddg10_`. Это подтверждает, что cookies устанавливает сторонняя инфраструктура Shikimori, а не аналитика YUME.

| Имя | Наблюдение | Рабочая классификация |
|---|---|---|
| `__ddg1_` | Непрозрачное значение, HttpOnly, около года | Вероятный защитный идентификатор DDoS-Guard |
| `__ddg8_` | Непрозрачное значение, около 20 минут | Вероятный краткоживущий защитный токен |
| `__ddg9_` | В одном ответе значение имело вид IP-адреса, около 20 минут | Вероятная техническая cookie фильтрации |
| `__ddg10_` | Числовая Unix-time-подобная метка, около 20 минут | Вероятная временная метка защитного механизма |

Поддерживающие публичные декларации: https://altex-com.ru/legal/cookie-settings, https://ainadesign.ru/cookies, https://afinaclp.com/privacy/. Официальные материалы DDoS-Guard: https://ddos-guard.net/file/cookie_en.pdf и https://ddos-guard.net/terms/general/cookie. В доступной документации поставщика нет авторитетной таблицы, подтверждающей точный смысл всех четырёх имён; описание каждого cookie остаётся рабочей классификацией, а не спецификацией.

**Решение:** не блокировать эти cookies вслепую, потому что они связаны с защитной инфраструктурой, обслуживающей изображения, и блокировка может сломать загрузку постеров. Это техническая оценка необходимости для сервиса, не юридическое заключение. Внешний скан оставляет эти cookies как не классифицированные, что указано ниже как ограничение.

## Проверка сценария согласия YUME

В свежем изолированном браузерном контексте до выбора не было `yume-cookie-consent-v1` и аналитических идентификаторов. После «Принять все» сохранялся выбор analytics=true, создавались visitor/session identifiers и наблюдались два POST к `/api/analytics` со статусом 200. Кнопка в футере открывает настройки повторно. После «Только необходимые» сохранялось analytics=false, оба идентификатора удалялись, а после reload новые POST к `/api/analytics` в наблюдавшемся интервале не появились.

В проверке первого слоя была видна только пара действий «Только необходимые» и «Принять все». Третий control настроек отсутствовал на самом первом слое, хотя повторное открытие из футера было доступно. Это устраняется отдельной кнопкой «Настроить» с выбором необязательной аналитики и сохранением granular choice; тест добавлен в `src/test/cookie-consent-settings.test.tsx`. Поведение после публикации новой версии требует повторной проверки live-версии.

## Внешний автоматический скан

Отчёт CertScore: https://certscore.ai/scan/9e917a22-3f17-4dd0-a571-0d00fb85124e

- Результат старого снимка: score 92/100, status `completed_limited`, риск-сигнал pre-consent storage classification review, плюс вопрос о видимости control настроек на первом слое. Это не юридическая оценка и не доказательство нарушения.
- Автоматический axe-core на ограниченной выборке starting-page: 0 зарегистрированных нарушений и 0 affected nodes; 177 наблюдаемых узлов, в retained примерах 5. Скан сам помечает покрытие как limited и не заменяет полный контрастный ретест.
- GPC: отправка `Sec-GPC: 1` и `navigator.globalPrivacyControl=true` наблюдалась, но вывод о соблюдении GPC остаётся indeterminate из-за неполного сравнения.
- CertScore не нажал Accept/Reject. Поведение согласия проверено отдельно вручную в изолированной сессии, описанной выше.
- Контрастные примеры 3.57:1 и 4.33:1 были связаны с текстом на ярком primary-цвете и приглушённой подписью в футере. На ветке исправлено: основной текст кнопок переведён на тёмный foreground через единый токен `--primary-foreground: oklch(0.16 0.04 285)`, а подпись футера больше не снижает opacity. По значениям CSS, стандартный расчёт sRGB даёт ориентировочно 5.24:1 для primary + тёмного текста (прежний почти белый текст давал примерно 3.68:1). Это расчёт token-level, не измерение каждого реального градиентного/overlaid компонента. После деплоя требуется повторный браузерный contrast test в разных темах; отсутствие ошибок в ограниченном axe-снимке не равно полной сертификации.

## Правила

- Не записывать будущие функции как действующие.
- Не утверждать, что сайт вообще не хранит IP: инфраструктурный поставщик может хранить логи независимо от D1.
- Не называть localStorage cookie, хотя можно описывать вместе как cookie и похожие технологии.
- Не считать закрытие баннера согласием.
- Для каждого нового поставщика фиксировать юридическое лицо, роль, цели, поля, место обработки, сроки, договор и дату проверки.
